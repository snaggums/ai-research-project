# VS-06.1 — Transcript Lifecycle Safety

## Vertical Slice

- **Name:** Transcript Lifecycle Safety — One Active Transcript
- **Version:** 0.1
- **Status:** Figma contract ready for review
- **Target duration:** To be estimated after the evidence-retention contract is approved
- **Owner:** Sky AIR
- **Depends on:** Session Transcript, Transcript Coding, Highlight, Code Suggestion, Session Report, and Record Synthesis contracts

## Product Goal

Give researchers a clear and safe lifecycle for the single active Transcript in
a Session. AIR prevents accidental duplicate uploads, provides explicit Replace
and Delete workflows, and never silently or ambiguously removes dependent
research evidence.

## Current Behavior

- A Session may upload and display multiple Transcript Documents.
- The first uploaded Transcript becomes the Primary Transcript.
- A researcher may attempt to make another Transcript primary.
- Delete and Set as primary use generic actions without a dependency preview.
- The backend rejects replacement or deletion when the existing Transcript has
  any Highlight or Code Suggestion Run.
- The current dependency guard is broader than accepted Highlights: uncoded
  Highlights and historical suggestion runs can also block the action.
- The interface surfaces the backend conflict only after the attempted action.

This produces an unclear hybrid workflow: the interface permits multiple
uploads, while the active Transcript Coding and synthesis contracts assume one
Primary Transcript.

## Approved Direction

- Each Session has exactly one active Transcript at a time.
- AIR prevents a normal second Transcript upload when an active Transcript
  exists.
- A Session with no Transcript exposes **Upload transcript**.
- A Session with an active Transcript exposes **Replace transcript** and
  **Delete transcript**.
- Replacement and deletion use an explicit confirmation contract that names
  the Transcript and explains every affected evidence category.
- Dependent evidence is preserved or deliberately removed according to the
  separately approved evidence-retention decision.
- True multi-Transcript Sessions are deferred to a later vertical slice.

An atomic replacement operation may temporarily store a replacement candidate
while it is uploaded and processed. The candidate is not a second active
Transcript and is not exposed as a normal second Transcript in the Session.

## UX Objectives

- Make the one-active-Transcript rule apparent before the researcher acts.
- Prevent an ordinary upload from creating a second active Transcript.
- Let a researcher replace the active Transcript without losing it when the
  replacement upload or extraction fails.
- Let a researcher delete the active Transcript after reviewing a specific,
  consequence-aware warning.
- Preserve focus, entered file selection, and existing research data after
  recoverable failures.
- Ensure that evidence lineage is never silently orphaned.

## Scope

### Included

- One active Transcript per Session at the interface and service boundaries.
- Upload availability when the Session has no active Transcript.
- Duplicate-upload prevention when an active Transcript exists.
- Explicit **Replace transcript** workflow.
- Explicit **Delete transcript** workflow.
- Dependency summary for the active Transcript.
- Confirmation dialogs with consequence-specific content.
- Atomic replacement processing and rollback behavior.
- Primary Transcript reassignment as part of replacement.
- Empty, uploading, processing, replacement failed, deletion failed, and
  successful completion states.
- Safe handling of existing Sessions that already contain multiple Transcript
  Documents.
- Query invalidation and Transcript Coding refresh after a successful lifecycle
  change.
- Audit-safe handling of dependent Highlights, Code assignments, Code
  Suggestions, Session Report evidence, Record Synthesis evidence, Themes, and
  conversation citations.

### Out of Scope

- Multiple active Transcripts in one Session.
- Transcript merging or concatenation.
- Coding across multiple Transcripts in one Session.
- Moving a Transcript between Sessions or Projects.
- Bulk replacement or deletion.
- Automatic remapping of Highlights to similar text in a replacement
  Transcript.
- Automatic deletion of existing duplicate Transcripts during migration.
- Tablet or Mobile Figma source variants unless explicitly requested.

## Product Rules

### One active Transcript

1. A Session with no active Transcript may use **Upload transcript**.
2. A Session with an active Transcript must not expose the normal upload
   workflow.
3. A direct API request that attempts a normal second upload must be rejected
   with a stable conflict code.
4. The active Transcript remains authoritative for Transcript Coding, search,
   Session Report generation, and future synthesis until replacement completes.

### Replace transcript

1. **Replace transcript** opens a file-selection and confirmation workflow.
2. The existing Transcript remains active while the replacement uploads and
   processes.
3. A failed upload or extraction leaves the existing Transcript and all
   dependent evidence unchanged.
4. The replacement becomes active only after server validation succeeds and
   the approved evidence-retention policy is applied transactionally.
5. The interface must not display the replacement candidate as a normal second
   Transcript.
6. Repeated or retried replacement requests must be idempotent.

### Delete transcript

1. **Delete transcript** always requires confirmation.
2. The confirmation identifies whether the Transcript is primary and lists
   current dependency counts.
3. When dependencies exist, the destructive action is not the default focused
   control.
4. Successful deletion leaves the Session with no active Transcript and
   exposes **Upload transcript**.
5. Deletion must be transactional and must not leave partial evidence removal
   or dangling ownership references.

### Existing multiple-Transcript Sessions

- Existing Transcripts and IDs are preserved during migration.
- No migration may automatically choose and delete a non-primary Transcript.
- The existing Primary Transcript remains active.
- Additional existing Transcripts require a reviewed resolution path, such as
  selecting one as the replacement or deleting it with the approved
  confirmation workflow.
- New normal uploads remain blocked while an active Transcript exists.

## Evidence-Retention Approval Gate

Implementation must not begin until one policy is approved for both Replace and
Delete. The policies may differ by action.

### Policy A — Preserve lineage

- Remove the old Transcript from the active Session workspace.
- Retain an archived or tombstoned source record and evidence snapshots.
- Preserve accepted Highlights, Code assignments, reviewed artifacts, and
  Record-level evidence lineage.
- Clearly label evidence whose source Transcript was replaced or deleted.
- Remove or protect the original uploaded file according to the approved data
  retention rule.

### Policy B — Remove dependent evidence

- Present exact counts and categories before confirmation.
- Remove dependent Highlights, assignments, suggestion runs and evidence, and
  any other approved downstream artifacts transactionally.
- Retain Record-owned Codes unless a separate Code lifecycle action removes
  them.
- Recalculate Record Code frequency, Session coverage, and accepted Highlight
  counts.
- Define how reviewed Session Reports and Record Synthesis artifacts with
  source references are invalidated, superseded, or removed.

### Recommended starting position

- **Replace transcript:** preserve prior evidence lineage unless the researcher
  explicitly chooses an approved destructive alternative.
- **Delete transcript:** require a consequence-specific confirmation; the final
  preserve-versus-remove behavior remains an approval decision.

### Approved MVP policy — July 28, 2026

- A Session has one active Transcript. A normal second upload is rejected.
- Replace keeps the current Transcript active while a candidate uploads and
  processes. Successful processing activates the replacement atomically and
  archives the previous Transcript.
- Delete removes the Transcript from the active Session workflow and retains a
  tombstoned source and dependent evidence for research traceability. Permanent
  data purging is deferred.
- Archived Highlights and Code assignments remain historical but do not
  contribute to current Session counts or Record Code aggregation.
- The current Session Report becomes superseded after replacement or deletion.
  Existing Record Synthesis remains historical and is marked out of date.
- Existing Primary Transcripts remain active. Additional legacy Transcripts are
  preserved as archived legacy sources and are never deleted automatically.
- Replacement activates automatically after successful processing. A failed
  upload or extraction leaves the current Transcript and evidence unchanged.

## User Stories

- As a researcher, I want AIR to prevent a second normal Transcript upload so
  that I understand which source is authoritative.
- As a researcher, I want to replace a Transcript safely so that a failed
  replacement does not destroy my current research.
- As a researcher, I want to see which Highlights and downstream artifacts
  depend on a Transcript before deleting or replacing it.
- As a researcher, I want deletion consequences stated explicitly so that I can
  make an informed destructive decision.
- As a researcher, I want accepted Record Codes to remain stable unless their
  source assignments are deliberately removed.

## Information Architecture

The workflow remains within:

```text
Project
  → Session
      → Transcript
```

No new primary navigation or route is introduced.

Session Transcript workspace states:

- No Transcript → **Upload transcript**
- Active Transcript → **Replace transcript** and **Delete transcript**
- Replacement uploading or processing → current Transcript remains active
- Replacement failed → current Transcript remains active; Retry and Cancel
- Replacement ready → approved confirmation and transactional activation
- Delete confirmation → dependency summary and explicit destructive action
- Delete complete → no-Transcript state

## Frontend API and MSW Deliverables

### Proposed transport concepts

- `TranscriptDependencySummary`
  - `is_primary`
  - Highlight counts separated into accepted and uncoded
  - Code Suggestion Run and awaiting-review counts
  - Session Report evidence count
  - Record Synthesis evidence count
  - Theme evidence count
  - conversation citation count

- stable errors:
  - `transcript_already_exists`
  - `transcript_confirmation_required`
  - `transcript_replacement_failed`
  - `transcript_dependency_changed`

### Proposed API boundary

The final route shapes require approval. The preferred direction is:

```text
GET    /api/projects/{projectId}/sessions/{sessionId}/documents/{documentId}/dependencies
POST   /api/projects/{projectId}/sessions/{sessionId}/transcript-replacement
DELETE /api/projects/{projectId}/sessions/{sessionId}/documents/{documentId}
```

- Normal upload returns `409 transcript_already_exists` when an active
  Transcript exists.
- Delete without the approved confirmation value returns a structured
  confirmation-required response.
- The server rechecks dependency counts inside the confirmed transaction.
- Replacement uses an idempotency key and never activates a failed candidate.

MSW fixtures cover no dependencies, each dependency category, dependency
changes between preview and confirmation, replacement success, processing,
failure, rollback, and legacy duplicate data.

## Database Changes

Database changes depend on the approved retention policy.

Possible additive fields or entities:

- Transcript lifecycle state: active, replacement candidate, archived, or
  deleted/tombstoned.
- `deleted_at` or `archived_at`.
- `superseded_by_document_id`.
- replacement request/job record with idempotency key and status.
- audit metadata for confirmed destructive actions.

Migration requirements:

- Preserve all existing Document IDs and Session relationships.
- Keep the current Primary Transcript active.
- Do not automatically delete legacy additional Transcripts.
- Make migration and any backfill replay-safe.
- Do not add a uniqueness constraint that prevents a transactional replacement
  candidate until the staging model is approved.

If the approved policy performs permanent cascading removal instead, the
service must explicitly reconcile every current `CASCADE`, `SET NULL`, and
`RESTRICT` dependency before schema changes are accepted.

## Accessibility

- Meet WCAG 2.2 AA.
- Confirmation dialogs name the affected Transcript and consequences.
- Dialogs trap focus, support Escape and Cancel, and restore focus to the
  initiating action.
- Initial focus does not land on the destructive action.
- Status and dependency meaning are not conveyed by color alone.
- Upload, processing, success, and failure updates use appropriate live-region
  announcements without moving focus unexpectedly.
- All file-selection and confirmation actions are keyboard operable.
- Destructive controls retain the approved AIR focus ring.

## Acceptance Criteria

1. A Session cannot create a second active Transcript through the interface or
   normal upload API.
2. A Session with no active Transcript shows **Upload transcript**.
3. A Session with an active Transcript shows **Replace transcript** and
   **Delete transcript** instead of normal upload.
4. A failed replacement leaves the existing Transcript active and unchanged.
5. A successful replacement activates exactly one Transcript.
6. Delete and Replace confirmation identify the Transcript, primary status,
   dependency counts, and approved evidence consequences.
7. No lifecycle action silently or partially orphans evidence.
8. Record-owned Codes are not deleted solely because one Transcript is removed.
9. Existing multiple-Transcript data is preserved until explicitly resolved.
10. The complete workflow is keyboard operable and passes automated
    accessibility checks.
11. True multi-Transcript Sessions remain unavailable and explicitly deferred.

## Risks and Dependencies

- Current evidence relationships use a mixture of database `CASCADE`,
  `SET NULL`, and `RESTRICT` behavior.
- Record Synthesis and reviewed Session Reports may prevent permanent Document
  deletion unless their lifecycle is explicitly reconciled.
- A generic “accepted Highlights” warning would miss uncoded Highlights,
  historical suggestion runs, and downstream evidence.
- Processing a replacement asynchronously requires a stable candidate and
  rollback contract.
- Existing Sessions with several Documents require non-destructive migration
  handling.

## Resolved Decisions

1. Replace preserves the prior Transcript and dependent evidence as archived
   lineage.
2. Delete retains a tombstoned source and evidence snapshots. Permanent purging
   is deferred.
3. The current Session Report is superseded. Record Synthesis remains
   historical and is marked out of date.
4. Source retention supports research traceability in this MVP; a separate
   administrative retention and purge policy is deferred.
5. Existing Primary Transcripts remain active and additional legacy
   Transcripts are preserved as archived sources.
6. Replacement activation is automatic after successful processing.
